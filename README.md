# dsh-exec-optimizer —— 执行优化

**输入栏右侧一个闪电图标，点开是七个开关。** 全部挂在 DSH **公开契约**的钩子上，
**没有一处包住模型调用**（不碰 `llm/stream`、不改模型目录、不动模型选择器）。

与 [`dsh-optimizer`](https://github.com/bigfatdsh/dsh-optimizer) 是两个独立插件：各自的包名、
各自的状态文件、各自的端点、各自的图标。两个都装也互不干扰。

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| 并行工具调用 | **开** | 在系统提示词里加一段纪律：互不依赖的工具调用必须放进**同一条消息**。宿主本来就会并发执行同一组调用，缺的只是让模型这么做——每合并一次就省掉一整轮请求。另外会盯着：连着三步都只发一个"本来可以并行"的调用时当面提醒一次。 |
| 失败重放 | **开** | 工具调用因参数错失败后，只发 `{"patch":{出错的字段:新值}}` 就能重放，不必把原来那一大坨参数整个重新生成。失败结果后面还会挂一行提示，点名是哪几个字段出错。 |
| 工具结果上限 | **开** | 超过 8192 字符的工具结果，在**写进会话之前**截头留尾，全文落到 `<DSH_HOME>/exec-optimizer-spill/`，结果里带路径。宿主自己的上限是 12500 token（约 5 万字符），这里更紧一档。 |
| 不动已发内容 | **开** | 把上限压到内置裁剪器（`tool-result-pruner`，8192 字符）的阈值以下，并**连 `read` 一起裁**——让它下一次压缩时找不到可裁的结果。已发出去的上下文因此永不被改写，供应商的前缀缓存不会从中间断掉。 |
| 复读抑制 | **开** | 连着两轮"没有工具调用、也没有新内容"的助手输出（例如反复 "Let me do it" "好。"）就插一条提醒；连到 4 轮直接停住这一步。带工具调用的消息一律清零。 |
| 按需加载工具说明 | 关 | 默认只把核心工具的 schema 发出去，其余留一个 `load_tools` 索引，用到再取。省下固定常驻成本，代价是工具表变化处会重建一次前缀缓存。 |
| 提前自动压缩 | 关 | 宿主的自动压缩线是 **678,464** token。打开后越过 30 万就主动压一次，不必等历史涨到 67.8 万。默认关闭：压缩会花一次摘要调用并改写历史。 |

## 它挂在哪儿（以及刻意不挂哪儿）

| 钩子 | 用途 | 为什么是它 |
|---|---|---|
| `systemPrompt.section` | 并行纪律 / 重放用法 / 按需加载用法三段文字 | 只加文字，不加工具；关掉时返回空串，零成本 |
| `tools/post-execute` | 结果发送前裁剪 + 失败调用记账 | 结果**还没进会话、还没发出去**的唯一点，改在这里才不破坏前缀缓存 |
| `tools.register` | `retry_tool` / `load_tools` | 官方注册面；只在对应开关打开时注册，关掉立刻摘下来 |
| `system-prompt/assemble` | 藏掉未加载工具的 schema | 每轮重新装配、返回值权威，是宿主给的按需加载点 |
| `session/event` | 观察助手消息 | 提交后的只读流水，用来数"复读连击" |
| `agent/pre-step` | 插提醒 / 提前压缩 | 每个 step 的起点，能改这一步进入的消息 |

**没有任何一处包住模型调用。** 测试里有一条专门断言这件事。历史上把宿主内存拖爆的正是
那类钩子（出站守卫、模型目录补丁、选择器补丁），这里一个都没有。

## 为什么这样是省 token 而不是省质量

- **并行纪律**：宿主 `dsh-agent-loop` 的 `executeToolCalls` 本来就把同一条消息里声明了
  `isConcurrencySafe` 的调用并发跑（上限 10），结果按模型顺序落库。所以这一项没有改变任何
  工具的行为，只是让模型少走几轮"一步一件事"。
- **结果上限**：裁掉的不是信息，是传输方式。全文一定落盘，路径写在结果里；模型要细节就
  自己 `read`（带 offset/limit）或 `grep`，只把真正需要的那一段拉进来。**落盘失败就不裁**
  ——宁可多花 token，也不给一个取不回来的残缺结果。
- **不动已发内容**：这是算术，不是策略。上限（8192）与内置裁剪器的阈值（8192）相等，
  裁剪器下一次压缩时找不到任何一条超阈值的结果，也就没有东西需要改写。
- **复读抑制**：判定口径刻意窄——带工具调用的消息一律清零，正常长度的回答一律清零，
  只有**连续的**碎片才算。
- **按需加载**：藏 schema 不藏工具。工具注册表没动，隐藏的工具按名字照样可调用；
  `load_tools` 只是把 schema 送到模型眼前那一步推迟到真正需要时。
- **提前压缩**：复算宿主的线（`min(1e6×0.8, 1e6−256e3−65536) = 678,464`），只在自己的线
  更低时才动手；一旦越过宿主线就交给宿主，绝不两边抢着压同一个会话。另有 120 秒冷却。

## 配置

在 `cordis.patch.yml` 的 `exec-optimizer` 那一行里改（**未知键会被拒绝，插件直接不加载**，
所以别写错名字）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `parallelDefault` / `retryDefault` / `resultCapDefault` / `cacheSafeDefault` / `repeatGuardDefault` | `true` | 五个安全的开关的首次装配默认值 |
| `lazyToolsDefault` / `autoCompactDefault` | `false` | 两个会改动历史的开关 |
| `resultCapChars` | `8192` | 结果上限（字符）；`cacheSafe` 打开时取它与裁剪器阈值的较小值 |
| `autoCompactTokens` | `300000` | 提前自动压缩的触发线（token） |
| `repeatStopAfter` | `4` | 复读连击到这个数就停这一步；`0` = 只提醒不停 |
| `lazyCore` | 空 | 核心工具名单（逗号分隔）；留空用内置默认 |
| `persist` | `true` | 开关写到 `<DSH_HOME>/exec-optimizer.json`，重启后保持 |
| `file` | 空 | 状态文件路径；留空用 `<DSH_HOME>/exec-optimizer.json` |
| `log` | `false` | 装配时打一行 warn，写明七个开关各是什么状态 |

开关状态改完之后**下一个模型步骤**生效。

## 和同 profile 里另外两个插件的关系（实测）

这台机器的 desktop profile 里还有两个插件碰同一批钩子，实测结论如下：

| 插件 | 碰哪个钩子 | 实测结果 |
|---|---|---|
| `dsh-tool-token-optimizer` | `tools/post-execute`（`prepend`，注册在**最外层**） | 它的 `inlineChars: 1600` **才是最终生效的那道裁剪**。本会话 689 条工具结果：中位 545 字符、p99 1,563、**最大 1,596**，没有一条超过 1,600。所以本插件的 8192 上限主要起"落盘 + 给取回路径 + 让内置裁剪器无事可做"的作用，最终大小由它决定 |
| `dsh-optimizer` | `agent/pre-step` + `session/event` | 互不覆盖：它管推理档位与花费，本插件管工具结果与提醒；两条监听在同一条瀑布上都正常（本插件已删除换档，不再碰 `agent/request`） |

**两条由此而来的设计决定**：

1. 本插件的裁剪取回路径（`Full text: <路径>`）**放在结果最前面**，不放中间——夹在中间会被下游那个 1,600 的裁剪器一起裁掉，模型就再也找不到全文了。
2. 本插件**不改**另一个插件的配置，也不假设它在不在：单装本插件时 8192 生效，两个都装时它的 1600 生效，两种情况下"已发内容不被改写"都成立（任何 ≤8192 的裁剪都让内置裁剪器无事可做）。

## 已知边界（没做到的不假装做到了）

- **并行纪律是"让模型做"，不是"强制模型做"**。宿主只在模型**已经**把多个调用发进同一条
  消息时才并发；插件没有办法把一条消息拆开或合并。这一项的收益取决于模型听不听话，
  实测口径在 bench 里标 `computed`。
- **`cacheSafe` 打开时 `read` 也会被裁到 8192 字符**。这是"让裁剪器无事可做"的必要条件
  （`read` 自己封顶 50KB，比裁剪器阈值大）。要看大文件请用 `offset`/`limit` 分段读，或读
  落盘的那份全文。
- **同时装着 `dsh-tool-token-optimizer` 时，最终大小是它的 1,600 字符**，不是本插件的
  8,192（实测本会话没有一条工具结果超过 1,600）。两个都想要更紧的裁剪就留着它；只要
  可回读的裁剪就把它关掉。
- **「提前压缩」在常规会话里是空转**：默认线 30 万 token，而常见会话峰值只有几万。
  它只在长会话里才动手。当前数值可以在端点的 `optimizations.contextTokens` /
  `hostCompactTokens` 里看到（前者是最近一次量到的上下文，后者是复算出的宿主线）。
- **失败重放只在"参数错"这类失败上划算**。工具名不存在、参数不是对象、参数超过 4KB、
  或失败发生在 `retry_tool` 自己身上时，一律拒绝并说明理由。
- **提前压缩的"省"是推算**：需要"会话会跑多少轮、每轮多大"这些本机没有的事实。bench 把
  假设与算式都写出来了。
- **按需加载的索引只在调用 `list` 时进上下文**，不是每轮常驻；但工具表变化处会产生一条
  `tool-addition`，前缀缓存从那一点起失效——这是它默认关闭的原因。
- **跨调用状态全部有界**：失败记录每 agent 3 条 × 64 个 agent；复读窗口每会话 6 条 ×
  64 个会话；已解锁工具用 `WeakMap` 挂在 agent 上；只存字符串与数字，不持有请求对象、
  消息数组或结果对象。agent 销毁时记录跟着释放。
- **不含**：精简化输出与花费预警在 [`dsh-optimizer`](https://github.com/bigfatdsh/dsh-optimizer)
  里，本插件不重复实现。

## 安装

作为 profile 的一个 bundle：

```jsonc
// ~/.dsh/profiles/<profile>/package.json
{
  "dependencies": { "dsh-exec-optimizer": "link:/path/to/dsh-exec-optimizer" },
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-exec-optimizer"] } }
}
```

它的 `cordis.patch.yml` 会把自己插到 Host 根部。宿主重启后，输入栏右侧出现闪电图标。
